# 多轮案件增量状态与定向恢复

## 已确认的失败原因

`after-sales-lookahead-v1/run-03/baseline.json` 第二轮把明确的序列号原文绑定到待回答的原包装要求，第三轮因此仍缺序列号。不能把它解释为已核验材料被遗忘。候选第三轮的独立需求与对话解释对执行限制不一致，修复只收到笼统错误。

## 设计与不变量

- 从既有成果建立 `codex/after-sales-incremental-state-v1`。沿用 Case/Evidence/Assessment/ToolLedger，不建立平行状态库。
- 新候选只替换 verification 槽；保留两步前瞻规划，产品入口不 promotion。
- 独立需求提取可读取当前案件的受信要求与待回答问题，不读取行动模型输出。材料事实带有案件、要求及 PROVIDED/DEFERRED 归属，仍须逐字来源、会话所有权和政策身份校验。
- 对隐式待回答绑定，只有独立提取给出唯一、同案件、同原文的明确归属时才能修正绑定。显式目标冲突、多项或歧义进入一次定向修复，仍失败则具体澄清，不执行写入。
- 执行限制分歧提供字段及原文反馈；不通过吞掉分歧或自动解除限制继续。限制与确认保持独立。
- 增量核验允许显式 PRESERVE 或 REASSESS。PRESERVE 必须引用仍有效的原评估，匹配要求的材料、政策、来源和时效不能变化；跨类型新增原文仍交给模型检查是否影响旧结论。模型错误或不确定不自动保留旧充分性。
- 仅对受影响要求重新生成完整核验结果；复用由宿主复制原结论和引用。更正、撤回、过期、来源变化或政策变化会阻止对应复用。
- 预检冻结模型输入与变化报告；落账前仍比较版本、来源、材料基础和政策。工具账本重放返回同一已提交报告，恢复不重复写入或计费。
- UI 从已提交工具结果展示新增、保留、重新核验及原因；核验提议与已提交变化有明确区别，缺失记录不生成替代事实。
- 同一轮批量更新只在最终回复中使用各案件的最后投影，避免已满足材料仍生成过期追问；中间工具结果和事件保持不变。
- 定向修复只沿用既有一次重试。批量修复反馈明确要求逐项更新、政策要求标识、逐字引用和父引用覆盖；修复后引用仍不合法则具体澄清，不扩大预算或继续写入。

## 持久化和兼容

独立需求的 `USER_FACT` 新增可选 `material_scope`，旧契约仍可读取。新的核验产物存入既有 `AfterSalesSemanticAssessment.payload`，无需新表或数据迁移。

`case_evidence_transition_assessed` 表示预检提议；真实 `tool_result.result.evidence_transition` 才表示已提交。后者带有评估编号、输入指纹、来源/目标案件版本，以及每项材料的前后语义状态、PRESERVE/REASSESS 和理由。ToolLedger 重放返回同一个已提交结果。

增量指的是评估状态与输出的变化：模型仍读取完整来源与新增原文以检查跨类型影响；没有承诺节约 Token，也没有把模型判断提升为客观事实。延期记录沿用既有 readiness 账本和界面，本组件只展示语义评估变化。

## 验证

覆盖乱序材料、同时多项、显式目标冲突、延期、纠正/撤回、过期/政策变化、模型失败与恢复。先通过离线完整回归，再固定数据与源码进行多次真实模型诊断，保留全部负结果。新机制只证明可执行和可审计，真实收益另行判定。
