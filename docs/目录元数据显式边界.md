# 目录元数据显式边界

## 问题

旧版 `analyze_request()` 会在几乎每个非人工转接请求上调用 `_catalog_terms()`。后者再隐式导入
`src.tools` 并执行 `get_catalog_facets()`，因此“你是谁”、当前时间、计算和订单查询也会遍历商品表。
复合请求的子句覆盖检查还会递归调用 Intake，使同一轮可能重复读取目录。

这条调用链有三个问题：目录访问没有能力归属，读取次数无法受控，Intake 的纯语义判断与当前数据库
状态隐式耦合。

## 边界

商品搜索、商品发现和商品比较在 `CapabilitySpec.metadata_dependencies` 中声明
`catalog.facets`。Intake 只有在已有的商品动作候选成立时，才能通过 `CapabilityRegistry.metadata_snapshot()`
解析该依赖；普通能力请求不会取得 Provider。`_catalog_terms()` 现在只消费显式传入的快照，不再导入工具
或访问数据库。

`CatalogMetadataProvider` 提供以下语义：

- 首次读取生成不可变快照，后续读取命中同一缓存；
- 快照包含 schema 版本、数据来源、内容指纹、内容寻址版本和 UTC 生成时间；
- `invalidate()` 使下一次读取重新加载，`refresh()` 立即加载并原子替换；
- 读取、失效和刷新由同一把可重入锁串行化，并发冷启动只执行一次 loader；
- 刷新失败不会覆盖上一份有效快照；调用方取得的 facets 是副本，不能污染缓存；
- `tools.configure_db()` 会显式失效快照，测试或运行时切换数据源时不会沿用旧引擎元数据。

该 Provider 只提供只读的目录语言与 schema 上下文，不执行商品搜索、推荐或任何副作用。业务工具仍由
现有 `ToolExecutor` 完成参数校验、预算、账本与事件记录；本改动没有增加平行 Runtime 或执行通道。

## 失效约定

当前目录写入发生在受控种子、测试或运维路径。改变类别、别名、可搜索规格或库存可见性后，写入方必须
调用 Provider 的 `invalidate()` 或 `refresh()`。商品价格、库存等交易事实仍在实际工具执行时读取，元数据
快照不能作为商品存在、价格或库存的完成证据。
