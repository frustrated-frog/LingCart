# 目标无损目录查询设计

## 1. 问题与边界

旧链路会把“所有商品按类目展示，并在类目内按价格升序”等复合需求压缩成一次
`discover_products(query="所有商品")`。工具实际拿到了更大的候选集合，但推荐工具只返回探索
slate，回复层又固定截取前四项；验证器只检查工具返回结构，最终仍把任务标记为成功。

这不是单个意图标签错误，而是从自然语言到执行、验证和交付的多次语义损失。本轮新增的目录
查询路径只解决可由本地商品目录回答的结构化问题，不把推荐、支付、退款或外部实时知识混入同一
协议。

## 2. 执行主链

```text
用户请求与对话历史
  -> BusinessObjective(CATALOG_QUERY)
  -> Independent Request Audit（原文反向覆盖）
  -> CatalogQuerySpec（受限 AST）
  -> CompilationCoverage（逐项编译覆盖）
  -> query_catalog（真实 SQLite / Repository）
  -> CatalogResultArtifact（持久化结果集）
  -> Operation Validator
  -> Goal Verifier
  -> Delivery Verifier
  -> React 结构化目录视图
```

模型只声明受限 AST，不能生成 SQL、Python、任意 JSONPath 或物理数据库字段。运行时继续复用
`CatalogMetadataProvider` 的内容寻址快照，以及 `CatalogConceptRegistry` 的版本化概念和 Codec。
规格字段通过 `CatalogFieldRef` 引用概念编号，只有 Kernel 能把概念解析为 `specs.*` 物理字段。

## 3. 语义模型

`CatalogQuerySpec` 明确区分以下维度：

- `scope`：全目录或当前会话的上一结果集；
- `availability`：全目录记录或仅可售库存；
- `filters`：核心字段谓词或版本化目录概念谓词；
- `partition`：展示分区，不等同于聚合；
- `ordering`：有优先级的稳定排序，缺失值固定置后；
- `selector`：全量、Top-K、分页、ArgMin 或 ArgMax；
- `metrics`：Count、Min、Max、Avg 或 Sum；
- `projection`：用户要求观察的逻辑字段。

Top-K 和分页必须声明确定性排序；聚合必须明确使用全量选择；分区后的有限选择目前拒绝执行，
避免系统擅自猜测“全局前 K”还是“每组前 K”。这类尚未定义清楚的语义必须扩展协议后再开放，
不能由执行器静默决定。

## 4. 无损编译与核验

每个语义节点都携带独立的 `requirement_id` 与原文 `source_quote`。编译器产生从要求到工具参数
路径的全量映射；映射缺项、重复或在执行时被替换都会被拒绝。

仅检查 AST 内部仍无法发现理解模型一开始就漏掉的要求。因此，每个 `CATALOG_QUERY` 在工具执行前
会触发一次独立 Request Audit。审查模型从当前人类原文与适用的人类历史重新枚举范围、筛选、否定、
分区、排序、极值、聚合、投影与完整性，再与提议 AST 做双向核对。`APPROVED` 必须同时覆盖每个
原文要求和每个已声明 AST 节点；`REVISE` 只允许理解模型修正一次，第二次仍未通过则禁止执行；
真正存在多义性的请求进入澄清状态。审查调用计入同一 Run 的模型预算，不读取 ACE 经验，也不执行工具。

审查协议只向模型暴露带 Objective 前缀的规范 `requirement_id`。若 Provider 仍从查询规格中复制了
不带前缀的 AST 短编号，运行时只在该短编号能唯一映射到一个规范编号时做一次本地归一化，并记录
`catalog_audit_protocol_repaired` 事件；未知编号和跨 Objective 的歧义编号继续失败关闭。这个修复不
再次调用模型，不增加计费，同时不会把模糊引用猜成某个要求。审查提示还显式提供执行器语义：分区
存在时排序在每个分区内保持，`availability=ALL + selector=ALL` 不增加可售限制，Projection 只声明
必须验证的值而不改变目录成员，避免审查模型把协议事实误判为需求缺失。

多轮对话中，审查条目还必须声明 `source_turn=LATEST|HISTORY`。真正参与本轮语义的历史约束必须像
当前要求一样绑定规范编号；仅用于说明“不继承上一轮独立目标”的历史内容使用 `NOT_APPLICABLE`，且
不得绑定编号。`NOT_APPLICABLE` 对当前请求禁用，避免审查模型借历史排除语义跳过本轮要求。若审查
响应违反 Schema、来源或编号约束，整轮最多允许一次模型协议修复；修复只能纠正结构，提示明确禁止
把 `REVISE/CLARIFY` 偷换成 `APPROVED`。重试和成功修复分别写入
`catalog_audit_protocol_retry` 与 `catalog_audit_protocol_repaired`，第二次仍无效则失败关闭。

三个验证层职责不同：

1. Operation Validator 检查结果产物、查询规格、结果成员、筛选绑定和编译证明是否一致；
2. Goal Verifier 重新检查筛选、分组、排序、选择器和聚合是否满足声明目标；
3. Delivery Verifier 检查请求全量交付时是否发生截断，并核对交付数量。

只有三层均通过，步骤才可进入 `SATISFIED`。验证结果与 `result_set_id` 会写入运行事件，Run
Inspector 可以区分“工具成功”“目标满足”和“结果完整交付”。

## 5. 结果集与跨轮语义

每次目录查询生成内容寻址的 `result_set_id`，身份覆盖目录元数据快照、目录数据指纹、查询规格、
父结果集、总体成员和交付成员。会话状态只持久化来源 Run、结果集编号、成员编号与数据指纹的紧凑
引用；完整结构化行保留在来源 Run 的持久化结果中，不塞入模型上下文。

因此后续“最便宜的是哪款”会编译为：

```text
scope = PREVIOUS_RESULT_SET
selector = ARGMIN(price)
```

运行时在工具调用前从来源 Run 恢复父结果集的冻结行，并校验成员列表与内容指纹，再把父编号写入
新产物。即使当前目录中的价格后来变化，“上一组里最便宜”仍针对用户实际看到的那一版结果求值，
不会静默改用新数据。刷新浏览器后，对话接口会恢复每条助手消息关联的持久化 Run 结果，前端仍能
重建同一个结构化目录视图。

省略了商品集合的“最便宜的是哪款”可以继承上一结果集；如果本轮明确给出“耳机里面”等类目范围，
且没有“刚才/其中/上一组”等结果集引用，则当前类目覆盖历史范围并使用 `CATALOG`。理解层会对
“显式类目 + 无引用标记 + PREVIOUS_RESULT_SET”的冲突做一次有界协议修复，防止旧结果集因历史
存在而被错误继承。

当前只保存当前会话最近一次目录结果集；“第一轮结果”“刚才第二组”等多结果集指代仍需后续引入
显式结果集栈或用户可见引用名。

## 6. 前端交付

聊天正文只给出结论摘要；完整商品行由 `catalog_query_result` 产物驱动。前端按真实 `groups`
渲染桌面表格，并显示匹配数量、交付数量、排序方式、目录快照、结果集编号以及目标/交付核验状态。
页面刷新不依赖浏览器临时状态恢复结果。

分页产物区分“选择器已经完整执行”与“整个匹配总体已经全部交付”，并显式给出 `has_more`、当前页、
页大小和下一页编号。Top-K 同样不会被前端误写成总体完整。聊天摘要会针对 Count/Min/Max/Avg/Sum
使用中文语义标签，ArgMin/ArgMax 根据真实目标字段回答，不再把库存极值错误描述为价格极值。

前端不会自行重排、补造或推导业务真相；它只投影后端已经核验的结构化产物。

## 7. 已验证行为

- 60 款种子商品按三个真实类目完整展示，每个类目内价格升序；
- 将全量结果人为截断为四条时，Delivery Verifier 拒绝完成；
- 伪造或遗漏 CompilationCoverage 时，工具拒绝执行；
- “耳机都有哪些”后追问“最便宜的是哪款”，只在前一结果集内执行 ArgMin；
- 修改当前数据库价格后再追问，仍在持久化的上一结果快照内执行 ArgMin；
- 将 ArgMin 结果伪造成总体内的非最小商品时，即使成员、指纹和计数自洽，Goal Verifier 仍拒绝；
- 分页明确区分结果选择完成与总体完整，并给出后续页证据；
- 独立需求审查能在执行前发现理解模型遗漏的价格排序，经一次修正后重新审查；
- 独立审查返回唯一 AST 短编号时能本地恢复为规范编号，歧义短编号仍被拒绝；
- 独立审查能区分本轮要求、适用历史约束和不继承的历史目标，格式错误只允许一次有界修复；
- 刷新页面后，结构化产物与跨轮结果集仍可恢复；
- 单元测试使用脚本模型，不产生公网模型费用；真实模型只用于显式浏览器 smoke。

## 8. 真实限制

CompilationCoverage 负责机械证明“已经声明的语义节点没有在编译时丢失”，独立 Request Audit
负责发现理解层遗漏或改写原文语义。后者提高了保证强度，但仍是模型审查，不是形式化自然语言证明；
它可能误判，因此必须保留失败关闭、一次修正上限、模型预算和完整审查事件，不能把审查通过宣传成
数学意义上的正确性证明。

基线运行时为多阶段目录路径预留 60 秒总时限、20 秒单次模型时限和 6000 completion tokens。它们是
硬上限而非调用目标；常规路径仍只调用一次理解和一次审查。相较原先 10 秒单次时限，这能减少推理型
Provider 尚未返回时触发第二次计费请求；`max_model_calls`、协议重试次数和总时限继续约束最坏路径。

目录概念仍由版本化注册表控制。用户询问尚未注册的商品属性时，系统应澄清或明确能力边界；不能
让模型直接猜测物理字段。新增属性应扩展 Concept/Codec、固定任务集和验证用例，再开放到查询 AST。
