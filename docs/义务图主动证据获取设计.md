# 义务图主动证据获取设计

## 1. 问题与目标

原有政策感知执行会按固定顺序扫描 `CasePlan.next_actions`：先找权威读取，再找用户补证、延期、审批和能力阻断。它已经能够安全推进案件，但没有显式回答三个问题：当前有哪些并存义务、每个候选动作能改变哪些状态、为什么选择这个动作而不是其它合法动作。

V4 将当前有效的政策义务和持久化计划编译为 `ObligationGraph`，再由有界求解器选择一步。目标不是让模型自由生成工作流，而是在 Policy Engine 给出的事实和 CasePlan 给出的动作面内，形成可验证、可替换、可审计的决策机制。

## 2. Harness 隔离

`after-sales-obligation-graph-v4@4.0.0` 是 research-only candidate。它继承 V3 的 case-first 与 Readiness 协议，只替换 planning 槽位中的动作选择机制：

- V1–V3 继续使用 `priority_v2`，保持既有确定性行为；
- V4 使用 `obligation_graph`；
- Stable Kernel、ToolExecutor、政策引擎、证据账本、审批协议和恢复语义保持不变；
- 产品入口不能直接选择 V4。

候选机制的假设是：先完整核验全部义务和行动，再优先无需打断用户的权威取证，并在用户动作之间比较结构化信息价值，可以减少不必要停顿，同时不放宽证据和审批边界。

## 3. 编译产物

一次求解产生四层稳定身份：

1. `CaseExecutionState.state_id`：绑定案件修订、政策裁决、计划、义务和原始动作；
2. `ObligationGraph.graph_id`：绑定图版本、义务节点、依赖边、候选动作和所有校验问题；
3. `CandidateSelection.selection_id`：绑定候选集合、排序策略和选中动作；
4. `ObligationActionDirective.directive_id`：绑定最终状态、操作参数和选择证据。

图中包含：

- 每项政策证据要求对应一个 `REQUIREMENT` 节点；
- `resolution` 节点依赖全部证据义务；
- 每个持久化 `next_action` 对应一个候选；
- 候选被归类为 `AUTONOMOUS / ASK_USER / WAIT / APPROVAL / BLOCKED / INVALID`；
- 候选保存原计划动作指纹、政策绑定、成本序和可解锁节点。

第一版政策要求仍是扁平集合，因此所有 Requirement 都直接阻塞 Resolution。图契约保留显式边，后续可以加入义务间前置条件，而不改变执行器入口。

## 4. 候选核验

求解前会核验所有候选，而不是只核验最终被选中的一个。任一伪造或失配动作都会使整张图进入 `INVALID`，执行器主动弃权，不会跳过坏动作后继续选择一个看似安全的候选。

主要约束包括：

- 权威自动取证只能针对未满足的 `AUTHORITATIVE_ORDER + ORDER_RECORD` 义务，操作必须是无需审批的 `continue_after_sales_case`；
- 用户补证只能针对未满足的 `CUSTOMER_ATTESTATION + CUSTOMER_STATEMENT` 义务，且当前不能已有有效延期声明；
- 等待动作必须与 Readiness 的 claim、证据类型、义务、政策版本和校验和完全一致；
- 退款提交候选只有在全部义务满足且政策结果为 `ELIGIBLE` 时才可进入审批边界；
- 人工能力动作只表示当前能力阻断，不创建人工任务或绕过业务边界；旧计划只记录稳定 evidence goal 时，仅允许唯一反解到一项当前义务；
- `NEEDS_EVIDENCE` 的每项未满足义务都必须有对应候选，`MANUAL_REVIEW` 必须有能力边界候选，`ELIGIBLE` 必须有显式审批动作；
- 政策结果必须是受支持枚举，并与当前案件状态一致；无需审批与无操作字段使用严格类型检查，不接受布尔或空值的相似表示。

这使图同时承担轻量 Process Verifier：除了检查单次工具是否合法，也能发现计划遗漏了必要步骤。

## 5. 确定性行动求解

当前求解器不使用未经校准的模型概率，也不伪造真实熵或成功率。它计算的是结构化 `information_gain_upper_bound`：一个动作最多能观测或满足自己的 Requirement；如果这是最后一个未满足义务，还可能解锁 Resolution。

候选按以下稳定序列比较：

1. 安全动作类别；
2. 信息增益上界（降序）；
3. 用户交互成本；
4. 工具调用成本；
5. 等待成本；
6. 风险序；
7. 稳定目标身份。

类别支配关系确保：

- 合法权威读取优先于向用户提问；
- 只有全部义务满足后才会请求明确授权；
- 用户明确延期的义务不会被重复追问；
- 没有可执行能力时保持阻断；
- 排序平局不会依赖数据库返回顺序。

这些成本是透明的序数证据，不是实验收益声明。PR2 可以在同一候选接口上加入更丰富的问题覆盖率、答案分支和真实成本估计。

## 6. 真实执行链

```text
持久化 CasePlan
  -> CaseExecutionState
  -> ObligationGraph 编译与全候选核验
  -> 有界候选求解
  -> ObligationActionDirective
  -> ToolExecutor 执行权威读取（如有）
  -> 校验输出与案件修订进展
  -> 政策重算、计划修订、重新建图
  -> 在补证 / 延期 / 授权 / 能力边界停止
```

图求解不直接执行工具。所有实际动作仍经过原有 ToolExecutor 的 schema、预算、deadline、幂等账本和错误归一化。退款提交仍不在自主动作面内。

## 7. 可观测性与恢复

每次 V4 求解追加 `case_obligation_graph_solved` 事件，保存完整图、验证问题、候选成本、选择身份和支配关系。后续 `case_obligation_verified`、`case_autonomous_action_selected`、`case_autonomous_action_completed` 与 `case_execution_paused` 继续形成同一 Execution Spine，并携带 graph/candidate 身份。

`autonomous_execution` 保存本轮全部 `obligation_graph_ids` 和选择模式。重启恢复后，相同持久状态会重新得到相同图与指令；实际工具副作用仍由 Tool Ledger 复用，不依赖求解器内存。

## 8. 当前限制与下一步

- 当前候选只来自持久化 CasePlan，不由模型发明替代工具路径；
- 信息价值是结构上界，尚未估计用户回答概率或问题覆盖多个义务的能力；
- 当前政策义务为扁平依赖，还没有条件分支和互斥证据路径；
- 同轮多义务更新仍沿用 V3 的单轴安全限制；
- 本阶段只做离线确定性回归，不运行真实模型对比，也不宣称任务成功率提升。

下一阶段可以在不改变 Stable Kernel 的前提下，引入问题候选编译：计算一个问题覆盖的未知变量、可能答案分支、解锁义务和交互成本，并用冻结任务集检验是否真正减少无效追问。
