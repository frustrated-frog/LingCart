# 工具参数边界与物理调用观测修复

## 问题

ACE 挑战集的真实 Smoke 显示，模型向 `discover_products` 提交了 `limit=30`。后端实际只接受 1 到 12，但自动生成的工具 schema 只暴露了整数类型，没有保留 `Annotated` 中的范围约束。无效参数因此到达业务函数，产生一次本可提前阻止的失败调用。

同一报告还出现“trace 缺少物理后端证据”的误报。原因不是工具没有执行，而是离线评测的物理调用观察集合晚于生产工具集合，没有包含 `discover_products`、`get_catalog_facets`、`read_clock` 和 `calculate`。

## 修复

- Runtime 生成函数参数模型时使用 `get_type_hints(..., include_extras=True)`，保留 `Annotated` 元数据；
- `discover_products.limit` 在正式 schema 中声明 `1..12`，非法值在 ToolExecutor 调用后端前被拒绝；
- 离线评测观察集合与当前生产只读工具对齐，trace 与物理返回能够互相核验；
- ACE Candidate 最多选择 8 条、5,000 字符经验，避免把 21 条 Playbook 全量注入每次决策。

## 基线兼容性

V5 的 `physical_tool_calls` 上限从 V4 的 74 变为 223，不代表本次修复新增了 149 次调用。相同 60 项、71 轮任务的业务 trace 仍为 70 次；差异来自 V4 没有观察已经真实发生的目录 schema 读取。旧 `baseline_v4.json` 保留不改，新的观测口径冻结为 `baseline_v5.json`，防止把测量修复伪装成旧基线兼容。

## 验证边界

离线测试能证明 schema 拒绝、物理证据和上下文预算生效，但不能证明 ACE Candidate 的成功率提升。首次挑战集 Smoke 的两个样本都失败，正式 8 案例对照尚未执行。
