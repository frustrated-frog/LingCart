# 材料变更协议与跨轮来源

本阶段从 `38f923c` 的已有成果继续，前瞻规划保持不变。

必须保持的不变量：

- 本轮材料更新只来自本轮 ADD / REPLACE；PRESERVE 不构成再次提供。
- 保留的事实连同来源整体复制，不能因重复文字迁移来源。生产消息使用持久化消息编号；旧契约没有编号时按原文摘要和范围验证，不伪造编号。
- 新候选模型只生成一种材料变更列表，单项与多项使用同一协议；旧入口继续兼容。
- 提供、延期、撤回、替换均有明确类型和本轮来源；宿主解析案件版本并编译到原有执行器。替换的撤回和新证据仍在同一工具事务中完成。
- 顺序更新、中断恢复、幂等、核验和确认继续通过原有 Stable Kernel；不得因为统一协议降低校验或增加模型预算。
- 仅改变 tool_protocol 槽，对照使用修复来源后的增量状态候选；开发诊断不作为 promotion 证据。

## 跨轮来源身份

请求入库时，把真实 `ConversationMessage.message_id` 写入同一事务的 Checkpoint，并重新封存校验和。历史消息把编号传到 `HumanMessage.id`，需求契约的 `SourceSpan` 可选保存该编号。

PRESERVE 复制原来的需求、范围和来源，不重新在当前文本中搜索。校验持久化来源时，验证原消息属于本次会话且为用户消息，然后核对完整原文摘要与引用范围。当前材料核对只接收本轮 ADD / REPLACE 的事实，因此连续两轮都说“完整”也不会要求再次提交上一项材料。

旧 Checkpoint 和契约没有编号时仍按原文摘要与范围验证，不自动迁移来源。运行中 STEER 形成的合成请求只有内容与原消息一致时才沿用编号。若无编号的历史文档已经离开可用上下文，核验会拒绝，不能据相同短句猜测来源。

## 已有案件的模型协议

研究候选 `after-sales-evidence-patch-v1` 在已有案件上下文中只展示 `material_changes`；初次建案沿用原来的 intake 协议，因为那时不存在可引用的要求编号。

| 操作 | 必填身份 | 含义 |
| --- | --- | --- |
| PROVIDE | requirement_id | 提供本轮材料，仍须独立核验 |
| DEFER | requirement_id | 明确延期提供，不表示材料满足要求 |
| RETRACT | evidence_id | 明确撤回当前案件的一条有效材料 |
| REPLACE | evidence_id、requirement_id | 明确纠正并替换同类材料 |

每项都必须包含 `operation` 和逐字引用的本轮 `source_quote`，父目标引用覆盖各项引用。同一要求只允许一个操作；替换通过 REPLACE 表达。编号必须来自可信案件账本，模型不能指定案件版本、澄清绑定或执行顺序。空列表或省略列表表示重新评估。

宿主验证协议后，编译为现有内部 `evidence_updates` 与顺序工具调用。旧 Profile 继续使用兼容协议。替换把撤回编号和新陈述传入同一个 `continue_after_sales_case` 事务；单纯否定旧事实不会自动授权撤回。

`material_patch_decoded` 事件标为 PROPOSED，只说明协议解码，不代表写入成功。真实入账与 UI 材料变化仍以持久化的工具结果、账本和证据转换为准。

## 评测边界

来源身份修复同时作用于对照两组。对照基线为 `after-sales-incremental-state-v1`，候选只替换 tool_protocol；规划、增量核验、模型与预算保持一致。开发诊断复用已冻结的两项多轮任务，每项每组重复两次，并核对实际入账材料类型及最终确认状态。正式 test Gate 的配置单独保存；这次开发诊断不能用于 promotion。
