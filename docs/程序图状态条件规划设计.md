# 程序图状态条件规划设计

## 1. 要解决的问题

V3 已经能把局部程序图编译为零额外模型调用的指导契约，也能阻止“完全相同的空结果/错误调用”立即重放。但自然语言 `condition` 只是说明文字：只要边被局部检索命中，就可能成为候选行动。另一个缺口是重放身份过去先于工具参数归一化计算，`keyboard` 与 `键盘` 可能被误认成不同调用。

V4 不让程序图接管 Runtime。它在 Stable Kernel 之外增加一个可替换的上下文策略：从权威轨迹投影有限事实，用受限条件协议做三值求值，再对当前适用的一跳边排序。权限、审批、预算、工具执行和终止语义仍由内核决定。

## 2. 受限条件协议

边条件不是 Python、JSONPath 或 Prompt 表达式，只能引用白名单事实，例如目标是否建立、未完成目标类型、最近行动及结果、结构化反馈和剩余预算。操作符同样按事实类型封闭。

求值结果只有：

- `TRUE`：证据存在且满足，边可以进入当前指导契约；
- `FALSE`：证据存在但不满足，边被排除；
- `UNKNOWN`：证据缺失或工具结果未知，边必须弃权，不能按“可能适用”执行。

每个子句同时保存实际值和权威来源路径。自然语言 `condition` 继续用于解释，但不参与机器判定。

## 3. 路径与行动边界

定位器仍负责选择锚点和有界局部图。V4 只对锚点的一跳出边做当前适用性判定；路径中的后续边仅用于排序和解释，并标记为“状态变化后必须重新求值”。因此一个两跳路径不能被模型一次性当成已经授权的计划。

排序由定位置信信号、未完成目标、历史 `pg_action_outcome` 和静态行动成本组成。它不读取隐藏思维，也不把一次采用当作成功。

## 4. 规范化执行身份

已有目标时，工具候选按以下顺序处理：

1. 工具 schema 校验；
2. 目录概念等可信适配器归一化；
3. 使用最终 `TaskStep.args` 计算执行身份；
4. 再执行 PG 契约审查；
5. 通过后才进入 ToolExecutor。

事件同时保留原始决策指纹、规范化执行指纹与参数来源，但不会记录密钥。首次“建目标 + 工具”的复合决策保留既有事务语义：合法目标先持久化，工具参数错误进入修复轮；之后的所有工具候选都在 PG 审查前归一化。

## 5. 真实进展归因

候选通过审查时保存一个小型执行前快照；行动完成后对比目标账本、证据引用、可信观察、映射修订和预算计数，持久化 `pg_action_outcome`：

- `PROGRESSED`：存在可验证状态变化；
- `NO_PROGRESS`：调用完成但没有新增目标、证据或可信观察；
- `FAILED`：步骤失败或被拒绝；
- `DEFERRED`：等待用户或外部输入；
- `UNKNOWN`：终止路径无法作可比判断。

结果以审查 ID 和步骤 ID 幂等关联。UI 与实验投影展示完整的“定位—条件—指导—行动—工具—进展”链；Refiner 只能把真实进展当作正向证据，更快失败不算收益。

## 6. 研究边界

V4 仍是 `candidate`，产品入口不能选择。离线 Gate 不调用模型，只证明协议和安全边界；正式收益必须使用冻结后新建的留出集，V3/V4 在相同模型、预算和源码修订上重复对照。测试集不得调参，负结果必须保留。

后续对照使用 `pg-state-conditioned-planning-v2` 契约：`adaptive-pg-v3-shared-graph-v1` 与 V4 读取同一 V2 图。进展快照已升级为内容身份比较，执行事实与信息增益分别记录；旧步骤计数事件不作为正向学习依据。见 [信息增益与公平对照修复](程序图信息增益与公平对照修复.md)。
