## 真实模型开发对照

通过现有 Gateway 调用 `deepseek-flash`。复用 `eval/after_sales_incremental_dev_tasks.json` 的逐轮乱序材料、同轮两项材料两个 dev 案例，每组每项各重复两次。每个 Run 最多 8 次模型调用，单次 Provider 尝试上限 1；16000 字符上下文和 45 秒预算保持不变。

基线是已包含来源修复的 `after-sales-incremental-state-v1`，候选仅替换 tool_protocol。完整通过需同时满足业务断言、当轮实际入账类型精确匹配、最终等待确认且无过期追问，并且没有未授权退款。原始逐轮事件、Prompt、源码/依赖/数据指纹保存在 `research/experiments/after-sales-evidence-patch-v1/run-01/`。

同版源码 `b0350e0` 的结果如下，两组源码树、模型、预算和数据指纹一致：

基线的五次修复包括三次建案字段位置错误、两次同轮材料拆分；候选的两次修复都是把补充材料错误解释成新增执行限制。后者被独立核验拒绝，随后在原有一次修复预算内完成。解码提议中可出现同一材料的重复记录，实际写入仍以已提交工具结果为准。

本批次没有观察到成功率差异；模型调用和 Token 较少只是小样本观察，不能归因为已经证明稳定收益。两组首次建案协议相同却出现不同修复次数，也说明模型采样波动存在。没有继续挑选最佳批次，没有增加预算或修改断言，也没有 promotion。完整摘要和校验和见 `diagnostic-summary.json`、`artifact-checksums.json`。

这是开发诊断，不是正式 test split Gate。撤回/替换及连续相同短答本轮仅有自动化回归覆盖，不能把两项 live 案例结果扩展到全部操作或任意复杂任务。正式评测配置已冻结在同目录 `experiment-spec.json`，本阶段没有执行该 test Gate。
