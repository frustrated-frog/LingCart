# 证据就绪度账本设计

## 1. 问题

售后案件里，“政策要求一种材料”和“用户现在能否提供这种材料”是两个不同事实。过去系统只能表达：

- 要求已满足；
- 要求未满足。

这会把两种状态压成同一个“缺材料”：系统不知道用户从未回应，还是已经明确说“稍后才能确认”。前者需要追问，后者应保留案件并等待。如果只把这句话塞进 Prompt 或临时计划，它会在进程恢复、案件重评估和政策切换后丢失；如果把它记成证据，又会错误放宽政策门槛。

本设计增加第三条独立事实轴：证据就绪度。它只描述用户当前提供材料的时间状态，不证明材料内容，不满足政策，也不授予提交或退款权限。

## 2. 认识论边界

| 事实轴 | 回答的问题 | 权威来源 | 能否满足政策 | 能否授权副作用 |
| --- | --- | --- | --- | --- |
| `EvidenceRequirement.status` | 政策材料是否已被核验为充分 | 证据账本、来源校验、语义核验 | 可以 | 不可以 |
| `EvidenceReadinessState` | 用户是否明确把某项材料延期 | 本轮用户原文、适用政策、案件事件 | 不可以 | 不可以 |
| `PolicyEvaluation` | 当前事实是否满足政策 | 版本化政策与稳定评估器 | 产生资格结论 | 不可以 |
| `PendingAction` | 用户是否确认具体高影响动作 | 绑定动作指纹的确认记录 | 不适用 | 只对绑定动作有效 |

当前版本只持久化 `DEFERRED`。`UNKNOWN` 不是事件，而是没有有效就绪度声明时的投影结果。这样系统不会把“没说”误写成“做不到”。

## 3. 执行链

```text
用户原文
  -> v3 对话协议提出 EvidenceReadinessClaim
  -> 新案件走 prepare_after_sales_case；已有案件走独立 readiness 写工具
  -> ToolExecutor 严格参数校验、幂等账本与串行写边界
  -> Stable Kernel 重新核验原文、会话、政策与义务
  -> 追加 EVIDENCE_READINESS_RECORDED 事件
  -> 政策输入身份更新，但政策充分性不变
  -> 案件计划投影 WAIT_FOR_CUSTOMER_EVIDENCE
  -> 执行器验证 claim / requirement / policy / plan 全链绑定
  -> WAIT_USER_INPUT，且不创建退款审批
```

模型只是声明候选。真正落账的权限和语义由稳定内核决定。

## 4. 不变量

### 4.1 声明必须来自当前用户原文

`source_quote` 必须是当前持久化 `AgentRun.request` 的逐字子串，且该 Run 必须属于案件的原始会话。历史摘要、模型推断、工具文本和其它会话都不能成为来源。

### 4.2 声明必须绑定当前政策义务

事件同时保存：

- `policy_version_id`；
- `policy_checksum`；
- `requirement_id`；
- `evidence_type`；
- `claim_id`。

只允许记录当前售后原因确实要求、且来源条件为 `CUSTOMER_ATTESTATION + CUSTOMER_STATEMENT` 的材料。订单记录等权威业务事实不能被用户的“稍后提供”覆盖。

### 4.3 声明不进入证据集合

声明只写入案件事件，不创建 `AfterSalesEvidence`，不产生证据校验记录，也不出现在 `active_evidence_types`。政策结果仍保持 `NEEDS_EVIDENCE`，不会因为声明变成 `ELIGIBLE`。

### 4.4 声明改变计划身份，不改变政策真值

最新就绪度事件的案件修订号进入政策输入哈希，保证旧决策和旧计划失效。计划可以从 `REQUEST_CUSTOMER_EVIDENCE` 变为 `WAIT_FOR_CUSTOMER_EVIDENCE`，但政策要求的 `SATISFIED / UNSATISFIED` 结果不变。

### 4.5 后续材料消费延期状态

投影器按案件事件序列处理。同类型的后续 `EVIDENCE_ADDED` 会移除当前延期投影；如果材料仍未通过来源或语义核验，计划会恢复为请求补充，而不是继续声称用户尚未准备好。

### 4.6 政策变化使旧声明失去效力

投影只接受与当前 `policy_version_id + policy_checksum + requirement_id` 完全一致的事件。政策切换后，旧声明保留在审计历史中，但不会自动迁移到新义务。

### 4.7 损坏或伪造绑定时失败关闭

`claim_id` 是事件规范载荷的确定性指纹。投影器发现事件版本、义务身份或指纹不一致时抛出 `EVIDENCE_READINESS_CORRUPT`，不会把异常数据降级成普通等待状态。

### 4.8 Profile 协议不能串用

v3 `readiness_ledger` 是 v2 `case_first` 的严格扩展，而不是替代协议：v2 和 v3 都允许 `evidence_context_quotes`，只有 v3 允许 `evidence_readiness_claims`。同一句话只能进入其中一个字段：没有明确稍后补充承诺的缺失或不确定性进入前者，明确延期且由用户控制的材料进入后者。字段会从未启用 Profile 的提示 Schema 中移除，解析后仍会检查当前绑定机制，防止模型自行注入协议。

### 4.9 恢复身份包含声明

证据语义核验的准备态键包含 `evidence_readiness_claims`。同一工具调用若改变声明内容，不能错误复用另一个声明的冻结准备态；工具账本、模型游标和稳定内核写入仍保持一致。

### 4.10 跨轮时间声明不触发证据语义核验

已有案件通过 `record_after_sales_evidence_readiness` 写入声明。它拥有独立的受控写策略、事务和幂等账本，不调用证据充分性模型，也不生成新的 `AfterSalesSemanticAssessment`。这样“我晚点提供”和“这是材料内容”不会共享模型判断路径。工具提交后仍重新生成政策决策与案件计划，使旧审批及时失效。

同一个目标不能同时延期并新增或撤回证据；复合诉求必须拆成可审计的独立目标，避免一个模型输出同时改变两条认识论轴。

### 4.11 跨轮上下文只暴露可信投影

下一轮模型不会从历史回复猜测等待状态。`current_case_context` 会用当前有效政策决策重新投影就绪度事件，再与最新有效案件计划按 `requirement_id` 对齐，只暴露紧凑的 `readiness.disposition/source_quote`、`next_action.kind` 和稳定等待原因。失效决策不暴露义务；事件版本、政策绑定或指纹损坏会失败关闭，不会降级成普通 `UNKNOWN`。

模型看到的投影只用于理解“案件正在等什么”，不携带授权能力。完整 `claim_id`、政策校验和、事件时间和案件修订仍保留在持久账本与计划中，由 Stable Kernel 在执行前核验，避免为了节省 Prompt 预算而削弱权威证据链。

## 5. 计划与执行验证

计划目标会携带完整 `EvidenceReadinessState`，等待动作只保存与它绑定的 `claim_id`。执行器只有同时验证以下条件才返回 `CUSTOMER_EVIDENCE_DEFERRED`：

- 要求仍未满足；
- 声明仍是 `DEFERRED`；
- `requirement_id` 和 `evidence_type` 一致；
- 政策版本与校验和一致；
- 计划动作的 `claim_id` 与投影一致；
- 决策、计划和案件修订仍有效。

任一绑定失败都返回 `ABSTAINED / EVIDENCE_READINESS_BINDING_INVALID`。系统不会根据展示文案或模型结论直接等待或执行。

## 6. Harness 隔离

`after-sales-evidence-readiness-v3` 当前版本为 `3.1.0`，是 research-only candidate，只替换 planning 槽位：

- Stable Kernel、ToolExecutor、审批边界不变；
- tool protocol 和 verification 机制与 v2 保持一致；
- 新增的是兼容 case-first 的对话协议、就绪度事件、计划投影与可信跨轮上下文；
- 产品入口拒绝直接选择该 Profile。

本阶段只完成机制实现和确定性回归，没有运行真实模型对比评测，也不据此宣称收益。

## 7. 当前限制与下一步

- 仅表达 `DEFERRED`，尚不接受模型生成的日期或提醒承诺，避免把模糊时间变成虚假 SLA。
- 就绪度目录来自版本化售后政策元数据，但 Prompt 目录不是授权源；实时政策始终由稳定内核重新核验。
- 声明只能说明用户何时能提供材料，不能验证陈述真实性。
- 当前没有主动提醒调度；案件只在用户再次进入时恢复。
- 同一目标暂不支持一边补充某项证据、一边延期另一项证据；需拆成独立目标和顺序执行。
- 附件、图像和外部凭证仍需各自的证据采集与来源验证协议。

后续可以在不放宽上述边界的前提下，引入由用户明确给出的 `available_after`、声明撤回事件和可恢复提醒调度，再单独冻结实验规格进行评测。
