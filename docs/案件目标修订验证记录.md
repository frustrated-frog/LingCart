# 案件目标修订验证记录

## 范围

候选为 `after-sales-goal-revision-v1`，基线为 `after-sales-model-planning-v2`。模型解释用户目标和材料；Stable Kernel 执行持久化、确认失效与副作用控制。没有新增依赖，没有为特定消费句子增加关键词路径。

新增回归覆盖双材料草稿、暂停后旧确认关闭、恢复重新核验、目标澄清但明确材料入账、非法材料不能释放暂停、两个崩溃恢复位置、跨 Profile 旧授权阻断、全局禁令保留、多案件目标覆盖及 API 状态投影。

## 自动化与浏览器

完整 Python 首轮 1229 项通过；补充全局禁令与案件模式并存等回归后，最终完整套件 1233 项通过，新增局部回归 15 项通过。离线任务 Gate 60/60，前端 98 项测试通过，类型检查和生产构建通过。

用测试模型生成真实 SQLite/Runtime 轨迹，再通过生产 API 与前端构建在桌面浏览器检查：草稿模式、用户原话、保留/暂停/下一步、已完成材料操作、被抑制的提交确认，以及记录选择器。浏览器控制台无错误，`/health` 与 `/ready` 正常，后者没有调用计费模型。这些界面检查使用脚本模型，不计入真实模型收益。

## 真实模型对照

源码冻结后运行五项 dev 场景、每组每项重复两次。每轮模型调用上限 8，每次 Provider 尝试上限 1。完成断言以外部任务结果、入账材料和新旧确认身份为准。

`run-01` 在源码复核时中断：发现全局 `NO_SUBMISSION` 不应被兼容逻辑自动转换为案件 `DRAFT`，也不应与明确 `CONTINUE` 冲突。四个已完成基线样本与中断原因全部保留，其中包含超时与入口失败；该不完整运行不用于比较收益。修正后在同版源码重新执行完整 `run-02`。

正式 test split 与晋升 Gate 尚未运行，候选未进入产品默认路径。既有全局禁令不会因恢复案件自动解除；旧 Profile 也会遵守保存的暂停状态，但不会解释新的案件目标修订。

## run-02 结果

固定源码 `520d909`，两组源码树、数据、依赖与预算指纹一致；模型为 `openai_compatible / deepseek-flash`。

| --- | ---: | ---: |
| 完整轨迹通过 | 2/10 | 5/10 |
| 普通材料回归 | 2/2 | 2/2 |
| 原 D05：双材料且只保存 | 0/2 | 1/2 |

| 提交／退款／付款工具调用 | 0 | 0 |

候选的三个新增通过样本分别来自原 D05 一次，以及目标澄清场景两次。观察到 DRAFT、PAUSED、CONTINUE、CLARIFY 四类目标进入真实运行。两次暂停都关闭了旧确认；但整条恢复任务仍未通过，不能把中间状态成功当成完整任务完成。

候选五条失败的原始原因：

- 原 D05 一次、草稿后恢复两次，在材料更新入口的原文／合法要求绑定校验失败。没有放宽来源校验来换取通过。后两条的后续恢复还出现 `SEMANTIC_EXTRACTION_INVALID / UNGROUNDED_REQUEST_IR`。
- 暂停再恢复两次，目标已变为 CONTINUE、案件也重新核验，但独立解释把“这句话不是同意提交”记成持久 `NO_SUBMISSION`，导致不生成新的确认。缺少授权与明确禁止执行仍需要更可靠的语义区分。

模型调用增加约 9.5%，不满足既有“模型调用不可回退”的门槛；不放宽门槛。基线存在用量缺失，不能计算可信的总 Token 节省或货币成本。小样本的延迟差异不能当成稳定收益。本次为 dev 诊断，未执行正式 test Gate、未晋升。
