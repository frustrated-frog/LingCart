# 售后案件与政策裁决设计

## 1. 目标

本轮建设的不是一个“退款对话流程”，而是可供 Agent 长时间协作、中断恢复和人工介入的售后业务底座。第一版先解决四个问题：

1. 售后诉求能够跨越多个 Run 和多轮对话持续存在；
2. 政策判断与 LLM 的语义理解分离；
3. 证据、裁决和状态变化都可回放、可审计；
4. 重试、并发和恢复不能重复提交或覆盖已存事实。

## 2. 领域边界

### Case 不等于 Run，也不等于 Conversation

- `AfterSalesCase` 是长期业务对象，表示一项持续的售后诉求。
- `AgentRun` 是一次可恢复的 Agent 执行尝试。
- `Conversation` 是对话上下文和用户交互容器。
- `AfterSalesCaseRun` 显式保存 Case 与 Run 的多对多关系，不把某次执行的临时状态当成业务真相。

### 订单必须精确到行项目

旧数据只有 `Order.item` 字符串。新增 `OrderItem` 后，种子数据会以加法方式为每个旧订单生成一个稳定行项目，不覆盖现有状态。当订单存在多个行项目时，创建案件必须明确指定 `order_item_id`，系统不会猜测用户指的商品。

## 3. 持久化模型

| 模型 | 职责 | 核心不变量 |
| --- | --- | --- |
| `OrderItem` | 订单行项目与金额 | 一个订单内行号唯一，金额使用最小货币单位 |
| `AfterSalesCase` | 长期售后案件 | `request_key` 幂等，`revision` 单调递增 |
| `AfterSalesCaseEvent` | 案件事件轴 | 只追加，事件序号与案件修订号一致 |
| `AfterSalesEvidence` | 证据信封 | 保存来源、内容指纹和观测时间，默认不信任证据内容 |
| `PolicyVersion` | 版本化政策 | 规则与 SHA-256 指纹绑定，旧裁决永久指向原版本 |
| `PolicyDecision` | 不可变政策裁决 | 保存输入事实、证据引用、理由码、允许动作和评估器版本 |

`PolicyDecision.case_revision` 是裁决的因果序号。不能只依赖 `decided_at` 选择最新裁决，因为两次评估可能具有相同时间戳。

## 4. 幂等与并发

- 案件创建使用全局唯一 `request_key`。同键同输入返回原案件，同键异输入返回 `CASE_REQUEST_CONFLICT`。
- 每个写操作使用案件内唯一 `idempotency_key`。同键异内容返回 `CASE_IDEMPOTENCY_CONFLICT`。
- 写操作必须带 `expected_revision`。数据库更新时使用 `WHERE revision = expected_revision`，冲突返回可重试的 `CASE_REVISION_CONFLICT`。
- 案件进入终态后禁止再次追加证据或改变状态。

## 5. 政策裁决

`AfterSalesPolicyEngine` 只产生裁决，不修改案件，也不执行退款。它读取权威订单、行项目、支付、现有退款、签收事件和有效证据，然后产生以下四种结果：

- `ELIGIBLE`：硬性要求满足，下一步只能请求用户确认，不会自动执行退款；
- `NEEDS_EVIDENCE`：缺少政策要求的证据；
- `INELIGIBLE`：已有足够权威事实证明不符合硬性条件；
- `MANUAL_REVIEW`：权威数据缺失、数据冲突或达到人工阈值，系统不得猜测。

裁决顺序先处理权威数据缺失和硬性拒绝条件，再检查证据与人工阈值。因此，已有退款申请不会因为同时属于高价订单而被误报为“待人工审核”。

## 6. Stable Kernel 接入

`AFTER_SALES_CASE` 是开放语义层中的显式 Capability。语义模型只能声明目标与已从用户原文落地的订单号，不能直接调用退款工具。编译后的执行链为：

```text
prepare_after_sales_case
  -> PolicyDecision
  -> prepare_case_submission
  -> 用户明确确认
  -> submit_after_sales_case
```

建案会写入内部业务事实，但不会触发退款，因此使用 `IDEMPOTENT_WRITE` 重放策略：必须在本地事务中与 Tool Ledger 原子提交，遇到可重试冲突时可以按相同参数有界重放。它不同于只读工具，也不同于需要用户授权的外部副作用。

提交工具仍使用 `REQUIRES_APPROVAL`。待确认操作绑定以下完整参数的 SHA-256 指纹：

- `case_id`；
- `expected_revision`；
- `decision_id`。

执行前会重新读取案件、政策和权威业务事实，并重新计算政策输入指纹。案件版本、政策裁决、支付状态、退款状态或日期事实任一变化，都会返回 `APPROVAL_STALE`，旧授权同时从会话中关闭，不能成为一个永久失效但仍可点击的待办。

## 7. 提交与恢复语义

- 同一次 Run 的建案事务与 Tool Ledger 同时提交。进程在工具提交后、事件写入前崩溃，恢复时会复用账本结果，不会再建一个 Case。
- 同一会话、同一订单、相同诉求文本的未终止 Case 可被后续 Run 重新关联和裁决；系统不会把匿名会话的案件跨用户复用。
- 确认 Run 会以 `SUBMISSION` 角色关联 Case。案件时间线因此能够区分受理、重新核验与最终提交，不用从聊天记录猜测。
- 退款写入、`AfterSalesCaseRefund` 关联、案件状态转移和工具账本处于同一个数据库事务。任何一步失败都会整体回滚。
- `AfterSalesCaseRefund` 对 Case 和 Refund 分别唯一，证明一个退款结果由哪次政策裁决和哪个提交 Run 产生。

## 8. 查询投影

只读接口直接读取案件账本，不从 Agent 回复文本推导状态：

- `GET /business/after-sales/cases`：按订单、会话和状态筛选案件；
- `GET /business/after-sales/cases/{case_id}`：返回案件、证据、事件、Run 关联、退款关联和适用政策版本。

政策详情保留版本号、来源、有效期、规则与内容指纹。UI 可以展示政策依据，但不能在浏览器中重新计算裁决。

## 9. 当前边界

第一条纵向链路先完成退款类 Case：自然语言建案、政策核验、跨 Run 记忆、明确授权、幂等提交、陈旧授权拒绝、状态追踪和查询投影均已接通。

以下能力仍属于后续范围，界面和文档不得暗示已经完成：

1. 用户上传图片或物流凭证后的补证交互；
2. 退货入库、换货、维修、部分退款和物流争议的执行工具；
3. 人工审核队列及人工裁决回写；
4. 退款提交后的异步处理、最终到账与 Case 自动完结；
5. 将旧的确定性 `REFUND_REQUEST` 评测契约迁移到新 Case 语义。当前旧路径为冻结任务集保留，新售后能力通过 Capability Registry 独立接入，避免在未版本化评测前静默改变历史基线。
