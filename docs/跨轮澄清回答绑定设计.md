# 跨轮澄清回答绑定设计

## 1. 要解决的问题

V5 能选择一个政策约束下最有价值的问题，但原实现只把问题放在当轮回复和运行事件里。下一轮出现“完整，附件也齐全”这类省略式回答时，如果只靠对话历史猜测对象，就无法证明回答对应哪个案件、哪个政策要求和哪个版本，也无法在恢复后可靠判断问题是否已消费。

5.1 把选中的问题建模为独立的 `AfterSalesPendingClarification`。它是等待证据的路由状态，不是授权状态，不能复用 `PendingAction`。

## 2. 持久身份与有效性

每条待澄清记录至少绑定：

- 会话、案件、来源 Run、案件修订号；
- `requirement_id`、`question_id` 与精确问题文本；
- Policy Version、政策内容指纹和 Policy Decision；
- Case State、Obligation Graph、Portfolio、Clarification Decision 与 Selection；
- 问题内容指纹、完整绑定指纹和确定性 `clarification_id`；
- `OPEN / ANSWERED / SUPERSEDED / CLOSED` 生命周期。

只有案件修订、当前裁决、政策指纹、当前 CasePlan 和问题文本全部一致的 `OPEN` 记录才会进入 `current_case_context`。政策或案件变化后，旧问题不会继续投影；终态事务会把它标为 `SUPERSEDED`。

## 3. 回答绑定协议

对话模型只看到问题 ID、要求、问题文本和状态，看不到内部 `clarification_id`。当当前原文回答唯一待澄清问题时，模型输出精确 `evidence_text`，运行时规范化器再从可信问题账本补入要求和内部绑定 ID。模型自行提交绑定 ID 会以 `UNTRUSTED_CLARIFICATION_BINDING` 拒绝。

`continue_after_sales_case` 在写入前重新校验：

1. 问题仍为 `OPEN`，且属于当前会话和案件；
2. 案件修订、要求、政策版本、指纹和裁决仍相同；
3. 问题和绑定内容指纹未被篡改；
4. 回答是本轮持久化用户请求的精确子串；
5. 该要求允许 `CUSTOMER_STATEMENT`，且独立语义核验已经完成。

校验通过后，证据、语义核验、Policy Decision、问题 `ANSWERED` 状态和 Tool Ledger 在同一数据库事务提交。绑定结果明确记录 `authorization_granted=false`；回答本身永远不直接满足政策或授权退款。

## 4. 恢复与审计

如果事务提交后、工具结果事件写入前进程崩溃，恢复路径先复用冻结语义输入，再从 Tool Ledger 读取已提交结果。工具处理函数不会重跑，因此不会重复证据、重复消费问题或重复推进案件版本。

Run Inspector 展示两类新事件：

- `case_clarification_opened`：问题已按案件与政策身份持久化；
- `case_clarification_answer_bound`：本轮原文已绑定，但仍等待语义与政策判断。

这两类事件与 `approval_required` 分开呈现，避免把回答材料误读为操作授权。

## 5. 当前边界

- 一次只消费一个问题和一个政策义务；
- 多案件时仍要求用户明确案件或唯一订单，不能用“最近问题”猜测；
- 回答可以被核验为充分、不完整、无关、冲突或未知；只有后续 Policy Engine 能改变资格结论；
- 真实模型评测暂缓，当前结论只来自离线契约、事务、恢复和界面回归。
