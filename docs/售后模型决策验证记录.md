# 售后模型决策验证记录

## 实现与边界

`after-sales-model-planning-v1` 只替换基线 `after-sales-evidence-patch-v1` 的 planning 槽：模型根据用户原文、保留的目标/偏好、当前政策状态及实际工具观察，选择合法动作或提出目标澄清。每次真实观察后重新判断，宿主继续控制参数、权限、幂等和确认。预计观察与重新规划条件始终作为假设展示。

这不是新的维修、换货业务工具，也尚未接入经验学习。可用动作仍来自现有能力与政策要求；模型不能生成任意工具或自行授权提交。目标澄清、非法输出拒绝和恢复幂等由自动化测试覆盖。

## 开发诊断约定

- 固定数据：`eval/after_sales_model_planning_dev_tasks.json`，三个 dev 场景，每个 Profile 各重复两次。
- 场景分别为“先包装后标签”“先标签后包装”“同时提供两类材料”。前两个场景还包含用户主动提供非当前所问材料的后续轮次。
- 完整通过要求：既有任务断言通过、第一问符合指定顺序、每轮恰好落账预期材料类型、最终等待确认且无过期材料问题。
- 模型为 `openai_compatible / deepseek-flash`；每轮最多 8 次模型调用，每次最多 1 次 Provider 尝试。预算、数据及两个 Profile 在每一批对照内相同且冻结。
- 金额成本没有经过验证的单价，报告保留 `null`；比较实际 Token、调用次数和延迟。

复现命令（输出目录必须尚不存在）：

```bash
venv/bin/python research/experiments/after-sales-model-planning-v1/run_smoke.py \
  --output research/experiments/after-sales-model-planning-v1/run-next
```

## 首轮负结果

`run-01` 固定源码 `976c625`。两组均仅完整通过 2/6，失败集中在包含处理顺序的两个场景。独立提取器已识别顺序边界，但分句覆盖检查只接受“引用在分句内”，拒绝跨分句的完整顺序引用，最终误导协议修复，无法建立案件。

公共入口修复允许经过独立核验的非结果需求完整覆盖一个分句；OUTCOME 仍必须有对应业务目标。没有增加请求关键词分支、放宽确认、提高预算或删除失败数据。延期测试也补充了真实落账断言：原测试未确认延期成功，修复后必须让模型替身显式引用待补材料，不能依赖已经关闭的旧问题。

基线/候选首轮分别为 36/41 次模型调用、142264/152141 Token。两组未出现评测器记录的越权写入或重复动作；入口失败期间几乎没有进入新模型规划器，因此本轮不能用来判断其顺序选择能力。

基线固定先问标签，因而两次“先包装”不满足顺序要求。候选四次指定顺序均符合，但 `MODEL-PLAN-D01` 第一次重复的第二轮发生 `INVALID_CASE_MODEL_DECISION`：两次模型输出的引用均未通过用户原文校验。系统保留已入账材料并停止该轮决策，后续用户补交仍能到达确认；此轨迹仍记为失败，不能用最终状态掩盖中途错误。

本批候选增加 15 次模型调用（约 25.9%），Token 增加约 10.2%。结论是小样本中模型确实改变了行动顺序，但也增加了协议失败点和成本；尚不能宣称总体业务成功率得到稳定提升。下一步应扩大独立任务验证，并改善决策引用的协议可靠性，不能靠放宽原文校验或增加重试掩盖失败。
