# 案件目标修订设计

## 不变量

- 用户目标按当前会话内的案件隔离，模式为 CONTINUE、DRAFT、PAUSED 或 CLARIFY。模型解释用户语义，代码执行模式对应的权限和终止约束，不匹配固定问句。
- 独立需求提取读取用户原文及可信案件身份，目标修订必须有本轮原文。未提及目标不改变旧模式；继续处理不等于确认提交，也不自动解除已有全局禁令。
- 明确材料可与目标澄清一起核验入账，目标不明时禁止自主推进和提交确认。材料本身归属不明则仍须先澄清，不能猜测。
- 模式变更关闭旧确认与材料问题；恢复重新读取和核验当前案件，再生成新的问题或确认。暂停不撤销已经入账的副作用。
- 目标状态、来源及计划差异保存在 Runtime/会话和事件中，恢复输入及版本号不因重放而变化。不存在第二套执行器。
- 新候选仅替换 planning 槽；旧候选保留，真实对照冻结同版源码、数据及预算。

原始 v2 轨迹重新核对发现：D05 的一个候选样本已完成材料写入，随后因缺少“保留草稿”的完成路径而进入 MODEL_GOAL_CLARIFICATION；另一重复才停留在入口。这修正了上一轮验证文档将两次失败均归为入口问题的说法。

## 接入与观察

候选 `after-sales-goal-revision-v1` 只替换 planning 为 `model-case-execution@3`。独立需求契约增加可选 `case_goal`，模型解释本轮原文，宿主验证案件归属；模型不会自己执行目标变更。原有全局禁止事项继续独立保存。`NO_SUBMISSION` 包含禁止退款的含义，核对时允许这种语义蕴含，但没有放松工具权限。

目标通过检查点和会话状态保存，`case_goal_revised` 记录来源、前后目标及执行影响；`case_goal_applied` 只在实际执行采用目标时记录，并携带已完成的材料操作。Run Inspector 从这些事件展示对照，不把计划当成完成。空记录、运行中、记录缺失和历史修订均有独立表现。

为了给历史和一次协议修复保留上下文预算，新候选不重复展开材料操作的四份来源字段 schema，仍在固定协议中声明全部字段，并通过同一 Pydantic 类型严格校验。没有扩大 Token、重试或工具预算。

## 冻结验证

正式实验门槛见 `research/experiments/after-sales-goal-revision-v1/experiment-spec.json`；正式 test Gate 不随开发诊断自动通过。开发诊断使用 `eval/after_sales_goal_revision_dev_tasks.json` 的五项 dev 场景，各组重复两次：普通材料回归、原 D05、草稿后恢复、旧确认暂停再恢复、目标模糊同时补充明确材料。

```bash
venv/bin/python research/experiments/after-sales-goal-revision-v1/run_smoke.py \
  --output research/experiments/after-sales-goal-revision-v1/run-next
```

基线与候选必须同版源码、同数据、同预算（每轮最多 8 次模型调用、每次 Provider 最多 1 次尝试）。完成标准同时检查外部状态、已入账材料类型和旧确认未被复用；不以候选特有字段作为胜出条件。开发测试通过也不代表正式晋升。
