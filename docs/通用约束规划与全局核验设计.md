# 通用约束规划与全局核验设计

## 1. 目标与边界

本轮解决的不是“400 元买耳机和键盘”这一句样例，而是一类结构相同的问题：用户同时提出多个有限候选目标，并要求它们共同满足总预算、相互比较、互异或显式优化条件。

系统遵守以下边界：

- Intake 只判断自己能否无损处理；不能完整表达时进入结构化理解，不直接宣判业务不支持。
- 模型负责把自然语言编译成目标图和约束 IR，不负责挑选候选、计算组合或自证正确。
- 候选事实只能来自已注册数据域 Provider；当前交付 `CATALOG`，求解器本身不认识商品、耳机或键盘。
- Stable Kernel 中的确定性求解器负责搜索，独立全局核验器从权威数据重新解析候选域并重算结果。
- 搜索未完成时可以交付已经验证的可行解，但绝不能据此宣称无解。
- 没有显式优化目标时，只按稳定差异覆盖策略选取若干可行方案，并明确说明这不是个人偏好排序。

## 2. 研究依据与工程取舍

### LLM+P

[LLM+P](https://arxiv.org/abs/2304.11477) 的核心分工是：LLM 把自然语言问题转换为形式化规划问题，经典规划器负责给出正确或最优计划，再把结果转换回自然语言。官方实现见 [Cranial-XIX/llm-pddl](https://github.com/Cranial-XIX/llm-pddl)。

LingCart 采用其中“语言编译与确定性求解分离”的原则，但不直接引入 PDDL。消费决策当前更接近有限域约束满足，因此第一版使用版本化 Constraint IR 和有界 CSP 搜索。

### LLM-Modulo

[LLM-Modulo](https://proceedings.mlr.press/v235/kambhampati24a.html) 强调 LLM 可以提出候选、补充近似知识或转换格式，但最终正确性应由外部可信 critic/verifier 保证。

LingCart 因此不接受模型输出的“总价满足预算”作为证据。工具执行完成后，全局核验器会重新读取权威目录、重建候选域、重跑求解，并比较整个稳定产物；任意价格、成员、约束观测值或 Provider 身份被篡改都会拒绝交付。

### 为什么第一版不直接引入 OR-Tools

[Google OR-Tools](https://github.com/google/or-tools) 是成熟的组合优化工具，适合后续 CP-SAT 求解后端。当前本地目录只有小型有限域，先实现可审计的求解器接口与严格失败语义，可以避免为了一个很小的问题引入重量级依赖。

求解器已经与数据域 Provider、Constraint IR 和核验器解耦；后续接入 OR-Tools 或 SMT 时应作为新的求解后端，不改变对话协议、能力注册表或全局核验语义。

## 3. 运行链路

```text
用户原文
  -> Intake：只能完整处理吗？
  -> Dialogue Understanding：ConstraintPlanSpec
  -> 独立需求覆盖审查：是否漏目标、改作用域、放宽约束
  -> Capability Registry：CONSTRAINT_PLAN
  -> Domain Provider Registry：解析权威有限候选域
  -> Generic Finite-Domain Solver：搜索可行赋值
  -> Global Goal Verifier：重新解析、重新求解、比较稳定产物
  -> Durable Run / Artifact / UI
```

任何一层失败都保留机器可读错误码，不会退回单商品推荐，也不会用模型自然语言覆盖失败状态。

## 4. 协议结构

### GoalNode

每个目标声明稳定 `goal_id`、原文证据、数量和候选数据域。数量默认是一件；大于一的数量必须能从用户原文中找到数值证据。

### CandidateDomainSpec

数据域只包含 `provider` 和 `parameters`。Provider 负责：

- 参数校验；
- 用户原文 grounding；
- 子需求枚举与编译覆盖；
- 权威候选解析；
- Provider 指纹、属性 schema 和来源证据。

新增数据域通过注册表接入，不修改通用求解器。测试中的非商品有限域证明了求解器没有依赖类目或商品字段。

### HardConstraint

第一版支持三类可组合硬约束：

- `AGGREGATE`：在一个或多个目标上执行 `SUM/MIN/MAX/AVG/COUNT`，再比较常量；
- `COMPARISON`：比较两个目标的归约属性；
- `ALL_DIFFERENT`：要求指定目标范围内某属性互异。

属性必须由所有受影响的数据域声明。无法解析的属性是协议错误，不会被解释成“没有可行解”。

### OptimizationDirective

只有用户明确表达最小化或最大化目标时才声明。未声明时不推断“越贵越好”“性价比最高”等偏好。

## 5. 搜索、完备性与失败语义

求解器执行有界深度优先搜索，并限制：

- 单数据域候选数量；
- 单目标数量展开后的选项数量；
- 完整赋值检查次数；
- 内存中保留的可行赋值数量；
- 最终交付方案数量。

当前实现没有使用假定数值非负的剪枝，因为通用 Provider 可以返回负值；错误剪枝会破坏完备性。

终态规则：

- 找到可行解：每个交付解必须逐约束通过，搜索可以是完整或有界的；
- 没找到解且搜索完整：允许输出 `PROVEN_INFEASIBLE`；
- 没找到解且达到搜索上限：输出 `CONSTRAINT_SEARCH_INCONCLUSIVE`，禁止宣称无解；
- 结果与权威数据重算不一致：输出 `CONSTRAINT_RESULT_EVIDENCE_MISMATCH` 并把产物标记为 `REJECTED`。

## 6. 可持久化与可观测性

每次执行持久化：

- `ConstraintPlanSpec` 与全部编译覆盖；
- Provider Registry 版本和每个数据域的 Provider 指纹；
- 候选数量及权威来源指纹；
- 搜索是否完整、检查数量和可行解计数语义；
- 交付方案、逐约束观测值和最终核验状态；
- `global_goal_verified` 或 `global_goal_rejected` 事件；
- 会话中的紧凑 `constraint_solution_set` 指针。

Run Inspector 和消费工作台读取同一真实产物。UI 只有在 `verification.status=VERIFIED` 时展示候选组合；否则只显示诊断证据。

## 7. 当前真实限制

- 当前只交付了 `CATALOG` 数据域 Provider；注册表和测试已覆盖非商品有限域，但还没有真实订单、优惠券或物流组合 Provider。
- 第一版是有限域枚举后端，复杂整数规划达到上限时会明确返回不确定，而不是尝试猜测。
- 软偏好、Pareto 前沿和可解释的多目标权衡尚未进入协议；当前只有硬约束和单一显式优化方向。
- 多轮修改可依靠对话历史重建完整目标图，并持久化上一版结果指针；还没有实现 IR delta 合并与增量求解。
- 本轮是论文原则的工程化接入，不宣称复现了论文原始实验结果。

## 8. 后续演进

1. 把求解后端抽象为版本化注册表，增加 OR-Tools CP-SAT 适配器和一致性差分测试。
2. 增加可构造 critic，把属性缺失、约束冲突和最小不可满足子集返回给理解层做一次有界修正。
3. 为多轮约束修改引入不可变 IR revision 和 delta compiler，保留每次修改的来源证据。
4. 建立跨领域固定任务集，比较直接 LLM、LLM + 自检和外部核验三条路线，保存全部负结果。
