# 流式回答与执行状态设计

## 目标

消费工作台需要在请求提交后立即给出反馈，并在 Agent 执行期间持续展示可公开的阶段状态和回答增量。该能力不能把流式传输误当成仅存在于浏览器中的视觉效果：刷新、断线和恢复之后，用户仍应看到同一条证据链。

本设计同时满足以下约束：

- 回答分片和阶段状态先持久化，再经 SSE 传给前端；
- SSE 只是落库事件的实时投影，不成为权威状态；
- 公开“理解需求、制定计划、调用工具、核验结果、组织回答”等粗粒度阶段，不公开隐藏推理过程；
- 已输出回答后不跨 Provider 自动拼接，避免把两个独立答案合并成一个看似完整的结果；
- 不依赖真实模型完成自动化测试，不增加付费调用。

## 事件协议

一次回答使用稳定的 `message_id` 标识，并产生以下事件：

1. `response_started`：回答开始，记录来源是 `model` 或 `assembled`；
2. `response_delta`：携带 `chunk_index` 与 `delta`，分片编号从 0 连续增长；
3. `response_completed`：记录分片数、字符数和完整内容的 SHA-256；
4. `response_failed`：记录机器可读错误码、是否已有可见前缀和已保存分片数。

`agent_status_changed` 只允许承载面向用户的阶段码与中文标签。当前阶段码包括：

`QUEUED / UNDERSTANDING / PLANNING / USING_TOOL / VERIFYING / RESPONDING / WAITING_USER / COMPLETED / FAILED / CANCELLED`

工具状态使用白名单中文描述；未知工具统一显示“正在调用工具获取证据”，不会把参数、观察结果、Prompt 或认证信息带入状态文案。

## 真实模型流与组装回答

最终模型轮通过 Model Gateway 的 `stream_once` 读取 Provider 原生流。Runtime 负责统一的超时、预算、错误分类、Provider 健康状态和事件持久化。

若 Provider 在尚未输出任何文本时失败，Runtime 可以按既有降级链重试。若已有分片对用户可见，则停止自动重试并写入 `response_failed`，因为切换 Provider 后续写会破坏回答的一致身份。

确定性快速路径、工具组装回答和澄清文案没有 Provider token 流。它们在终态提交前通过相同协议发布 `assembled` 回答分片，因此前端只有一种消费方式，也不会伪装成模型逐 token 生成。若最终模型流内容已与终态回答一致，Runtime 会复用已经完成的流，避免重复显示。

## 顺序与恢复不变量

- 每个事件都使用 Run 内单调递增的 `sequence`；
- 回答必须满足 `started -> delta* -> completed|failed`；
- `response_completed` 的分片数和内容哈希必须能由已保存分片复算；
- 完整回答事件先于 Run 的 `terminal` 事件；
- 最终结果、终态事件和会话 assistant 消息仍由 `RunStore.finish` 在一个事务中提交；
- 前端以 `sequence` 去重，并只展示从 0 开始连续的分片前缀；
- SSE 重连同时发送 `after` 与 `Last-Event-ID`，服务端只重放游标之后的落库事件；
- SSE 断开不会改变 Run 状态，前端会有界退避重连，轮询结果仍作为终态兜底。

## 前端交互

用户发送消息后，界面立即插入 Agent 占位回答，不等待 `/runs` 返回。服务端接受任务后，该位置依次展示公开阶段、已到达的回答文本和流式光标。连接中断时显示“连接恢复中”，已显示文本不会清空。

消息区域只在用户仍停留于底部附近时自动跟随新内容；用户向上阅读历史消息后，不会被新分片强制拉回底部。状态区域使用 `aria-live` 和 `aria-busy`，保证辅助技术能感知执行变化。

## 验证边界

自动化测试使用本地流式模型替身，覆盖：

- 分片顺序、去重、缺口与冲突；
- 部分输出后的失败不重试；
- 模型流与最终持久回答去重；
- 状态、回答与终态事件顺序；
- 前端请求提交空窗、回答增量投影和公开状态呈现；
- 轨迹投影对回答流完整性的校验。

真实 Provider 的网络兼容性属于显式人工 smoke 范围，默认测试和 `/ready` 不发送计费请求。
