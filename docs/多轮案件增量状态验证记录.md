# 多轮案件增量状态验证记录

日期：2026-11-01。分支：`codex/after-sales-incremental-state-v1`。本阶段从已有前瞻成果继续实现，没有修改产品默认 Profile。

## 实现与实际修复

- 新研究候选 `after-sales-incremental-state-v1`：规划和工具协议沿用 `after-sales-lookahead-v1`，只替换 verification 槽。独立需求提取读取当前案件要求与待回答问题，不读取行动模型的计划。
- 修复明确材料被隐式追问错绑：例如正在问原包装，但用户明确补充序列号时，独立归属可以校正隐式绑定。显式冲突、缺项或歧义最多修复一次，仍不一致则具体澄清。
- 增量核验显式选择 PRESERVE / REASSESS。宿主复制有效旧结论，新增材料、撤回、时效或来源变化阻止不合法复用；模型仍检查完整原文中的跨类型影响。模型失败不沿用旧充分性。
- 批量同源材料按材料类型绑定不同证据编号。同轮后续更新使中间追问过期时，最终回复只采用各案件最后的投影；历史事件仍保留。
- 修复后引用仍不合法时转为材料澄清，不再直接报通用执行失败。反馈只包含相关修复要求和字段，保持原有上下文与重试预算。
- 只有真实案件存在时才给独立提取器材料归属协议；初次建案不要求生成尚不存在的案件/要求编号。混用批量与单项材料协议的重复失败同样转为澄清。
- Run Inspector 增加材料前后状态对照、首次/重新核验/保留结论、中文原因、归属校正、版本与评估指纹。只把已提交工具结果显示为落账变化；预检提议、缺失、异常和历史状态有明确表达。

没有新增数据库表或依赖，复用 Case、Evidence、Assessment、ToolLedger 和 Gateway。候选不能从产品入口运行；用户仍须明确确认高影响操作。

## 真实模型开发诊断

统一 Gateway 的 `deepseek-flash`，固定 `eval/after_sales_incremental_dev_tasks.json` 中两个 dev 案例：逐轮乱序材料、同轮两项材料。每个 Profile、每个案例各重复两次，单次 Provider 尝试上限 1，Run 最多 8 次模型调用，保留 16000 字符上下文与 45 秒预算。

完整样本必须同时满足原有业务断言、每轮材料类型精确匹配、最终停在等待确认、没有过期追问和未授权退款。仅“工具调用成功”不算完整通过。源码、Prompt、依赖、数据指纹以及完整逐轮输出均保存在 `research/experiments/after-sales-incremental-state-v1/run-*`。

首轮 `run-01`（`a1c2af9`）中，基线通过 1/4，候选通过 3/4。基线出现序列号错绑原包装、同轮遗漏材料、执行限制分歧；候选的一次失败是批量修复后生成了不合法引用，返回 `UNGROUNDED_EVIDENCE`。该负结果完整保留，由此补充定向批量修复与失败后的澄清回归。

`run-02`（`c5458bd`）中，基线 1/4、候选 2/4。候选出现批量/单项字段混用，以及建案阶段直接澄清，随后没有案件可继续。混用字段的重复失败补充了澄清回归。

`run-03`（`936382f`）中，基线 1/4、候选 1/4。候选两次在尚未建案时生成无效材料归属、一次批量修复触及上下文上限；据此修正空案件上下文的提取协议。预算上限保持不变，上下文不足仍是显式终止原因。

四个批次的候选结果依次为 3/4、2/4、1/4、3/4，基线均为 1/4。不同代码批次不能合并为一个成功率。最终样本数很小，候选调用和成本也更高；收益尚不足以支持 promotion。完整摘要见 `diagnostic-summary.json`，原始报告与文件校验和分别见 `run-*/*.json`、`artifact-checksums.json`。

## 结论边界

这是开发集诊断，包含已经见过的失败类型，并非未见任务上的正式 Gate。没有宣称泛化提升，没有 promotion，也没有自动学习或修改 PG。独立核验仍可能与行动模型共享错误；材料充分只是用户陈述满足要求，不是独立验证了客观事实。

增量状态并不等于降低成本：新增归属信息和修复可能增加输入、输出与耗时。机器报告中通用 `policy_autonomy.case_resolution_rate` 针对另一类自动查询任务，本组没有对应标签，不应据此解释为退款完成率。所有样本都停在确认前，不执行退款。

后续需要冻结未见、多案件、长会话、模糊省略、矛盾更正与来源时效变化的测试集，增加重复次数，并同时约束完成率、错误材料归属、确认边界及调用成本。当前仍不能保证任意复杂任务准确完成。
