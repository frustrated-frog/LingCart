# 统一请求语义契约设计

## 目标

`RequestIR v1` 解决 Adaptive Shopping 与注册能力对话链路各自解释用户语义、却缺少共同审计表示的问题。它不替代现有目标、目录 AST、约束规划或售后案件状态，而是在这些协议通过各自校验后，生成一份稳定、可持久化、可展示的语义投影。

模型仍负责提出语义分类；Stable Kernel 负责原文定位、引用关系和执行权限。RequestIR 不能授权工具，也不能把事实声明直接升级为权威事实。

## 契约

当前版本为 `request-ir/v1`，要求类型包括：

- `BUSINESS_OUTCOME`：用户要完成的业务结果；
- `USER_FACT`：用户提供的上下文或事实声明，使用前仍需按来源核验；
- `PRODUCT_PREDICATE`：可映射到商品证据的单商品硬条件；
- `CROSS_GOAL_CONSTRAINT`：跨目标的聚合、比较或去重约束；
- `SOFT_PREFERENCE`：可以影响排序，但不能决定完成状态；
- `PROCESS_INSTRUCTION`：排序、投影、分组等执行或交付要求；
- `EXECUTION_BOUNDARY`：核验、证据和真实性等正向流程边界；
- `PROHIBITION`：明确禁止执行的动作；
- `UNKNOWN`：需要保留并澄清的实质不确定项。

每项要求都绑定 `SourceSpan`。Span 的 `start/end`、原文切片和消息摘要由宿主从 HUMAN 消息确定性生成，模型不能提交坐标。当前轮优先于历史；绑定历史时记录原消息序号与全文摘要。

## 不变量

1. `BUSINESS_OUTCOME` 必须引用目标，不能引用约束。
2. `PRODUCT_PREDICATE` 与 `CROSS_GOAL_CONSTRAINT` 必须拥有稳定的约束引用。
3. `EXECUTION_BOUNDARY` 与 `PROHIBITION` 不能携带目标或约束引用，因而不能被编译为商品条件或业务动作。
4. RequestIR 只投影已经通过来源校验的结构，不从助手历史、工具返回或模型说明中建立用户要求。
5. 相同输入产生相同的内容摘要；运行事件、检查点、HTTP 响应和工程页使用同一投影。

## 当前接入

- Adaptive 路径在独立目标审查通过后生成 RequestIR，随后才接受目标并执行工具。
- 普通对话路径在来源与能力参数校验后生成 RequestIR，并随 `TaskIntake` 进入计划编译。
- Run Inspector 的“上下文与证据”页展示完整 IR、语义要求数量和原文 Span。
- 独立审查协议已区分流程边界、禁止操作、用户事实与软偏好；这些类别默认不获得任何可执行引用。

## 后续边界

v1 先统一可追溯的语义类别，不合并两个执行引擎，也不改变现有工具权限。后续版本可以让普通对话协议显式声明流程边界，并让通用 `FailureSignature` 引用 RequestIR 的要求身份；在此之前，不应根据中文关键词从原文反推授权或偷偷修改已接受语义。
