# 售后有限步信息前瞻

基线 `after-sales-active-clarification-v5` 与候选 `after-sales-lookahead-v1` 只改变 planning 槽。两者共享请求理解、独立材料核验、工具账本和恢复实现。没有新增模型调用或依赖，没有 PG 学习更新。

## 两层验证

1. `experiment-spec.json` 冻结既有售后业务任务的同版回归条件：每项两次，正确率、稳定性、安全与协议不允许退化，模型尝试数不增加。该任务集已见，仅用于回归，不能支持未见任务泛化或前瞻收益结论。这里的零改善门槛不是 promotion 资格。
2. `eval/after_sales_lookahead_dev_tasks.json` 是新开发诊断：先开放案件，再补序列号，最后补包装和附件，要求只停在明确退款确认前。V5 / 候选各运行一次，保留失败，不充当正式收益评测。

运行开发诊断：

```bash
venv/bin/python research/experiments/after-sales-lookahead-v1/run_smoke.py --output research/experiments/after-sales-lookahead-v1/run-01
```

输出目录必须不存在。每轮预算沿用 Runtime，最多八次模型调用、单次请求最多一次 Provider 尝试，数据库隔离。报告含源码、Prompt、Profile、依赖和数据指纹及完整逐轮事件。

待补材料的前两轮允许既有协议的 `PARTIAL`（任务尚未完成），但必须没有错误和退款提案；另行检查首轮有绑定问题、补序列号后只追问包装、末轮等待明确确认。候选还必须记录两条不同首步路径。自动化业务断言和这些 `diagnostic_checks` 都满足，才算诊断通过。

`run-01` 保留首次负结果：开发夹具误用了不受支持的 `CUSTOMER_TEXT` / `SEMANTIC_SUFFICIENCY`，两者均在建案时被 `POLICY_SCHEMA_INVALID` 拒绝。它没有测到规划机制，不能用来判断 V5 或前瞻优劣。之后改用实际协议 `CUSTOMER_STATEMENT` / `CUSTOMER_ATTESTATION`，并添加调用模型前的隔离库政策校验和 pytest 覆盖。待补材料状态也依据现有离线 Runtime 的 `PARTIAL` 行为冻结。

`run-02` 使用修正后的夹具和相同提交 `e46e491`：V5 在补序列号时改为澄清，末轮独立需求修订校验失败；候选成功写入序列号并转问包装，末轮因混用批量/旧材料协议进入一次修复，但修复 Prompt 超过 16000 字符而停止。两者均未完整通过，保留全部原始记录。候选的回复渲染还漏接新模式，导致已选一问却向用户列出全部问题。

后续修复只让回复消费已选问题、去掉模型侧 Schema 中被 enum/const 完全约束的冗余类型声明，并精简重复固定说明。材料事实、原文、最终验证、修复次数和 16000 字符预算保持原约束。新增第三轮冲突协议修复与回复只显示选中问题的回归。不同提交的诊断不得合并计算收益。

最终 `run-03`（`f97480a`）仍为两者各 0/1 完整案例通过：V5 末轮重新缺少序列号，候选末轮 `REQUEST_SEMANTICS_MISMATCH`（执行限制判断不一致）。两者前两轮通过，候选记录两条首步路径。全部产物见本目录 `diagnostic-summary.json` 与 `artifact-checksums.json`，详细自动化和浏览器记录见 `docs/售后前瞻验证记录.md`。保持 candidate，不宣称收益。

## 判断边界

单元测试用两项材料、不同首步负担，验证相同两步覆盖下 V5 与候选选择不同，以及延期义务保留、审批、跨轮重新规划、崩溃后账本复用。它证明机制运行，不能替代真实用户回答成本的测量。

当前没有回答成功概率；两步充分信息分支只是乐观覆盖上界。未来若要 promotion，需要新冻结的未见任务、充分重复，以及真实完成率和回答负担对照。无效材料、拒答、纠正和工具失败也应进入该对照。
