# ACE Context V1 挑战集设计说明

## 目标

现有 `adaptive_tasks.json` 的冻结测试集已经达到天花板，最多用于验证 ACE 不退化，不能证明经验上下文带来收益。`ace_challenge_tasks.json` 是独立留出集合，不参与 Reflector、Curator 或 Playbook 调整，用于检验：

- 新约束组合是否能被完整保留；
- 多品类和三个独立目标是否发生遗漏；
- 跨轮修订是否覆盖旧约束；
- 价格、库存变化后是否拒绝过期证据；
- ACE 中以耳机任务为主的经验是否对键盘任务造成负迁移。

## 数据边界

挑战集包含 8 个 `test` 案例，不提供可用于调参的 `dev` 样本。其 `split_counts` 固定为 `{"test": 8}`，评测入口会核对声明数量和实际案例，防止增删案例后继续复用旧报告。

虽然数据使用本地虚构商品目录，但每个结果都必须经过真实工具、当前数据库事实、目标账本和独立审查；不能由评测器直接提供正确答案。

## 对照契约

正式对照固定在 `challenge-experiment-spec.json`：

- Baseline：`adaptive-v1`
- Candidate：`adaptive-ace-context-v1`
- 唯一机制变量：context 槽位的 `ace-playbook-context`
- test 重复次数：2
- 主指标：`mean_success_rate` 必须至少提升 0.01，且不允许正确率回退
- 保护指标：首次通过、全重复稳定性、安全和协议违规均不得退化

如果 Baseline 已经 16/16 全部通过，则该挑战集仍然出现天花板，不能据此宣称 ACE 有收益；应保留结果并重新设计真正能区分策略的未见任务，而不是放宽 Gate。

## 成本控制顺序

正式对照最多需要 Baseline 16 个样本和 Candidate 16 个样本，不能直接执行。顺序必须是：

1. `--dry-run` 校验 8 个案例、Profile、split、重复次数和实验契约；
2. 使用 `--case <ID> --repeats 1 --max-samples 1`，选择一个案例分别做 Baseline/Candidate 单样本 Smoke；
3. Smoke 中机制身份、独立审查隔离和执行证据全部正确后，才运行一次 8 案例 Baseline；
4. Baseline 没有天花板且失败具有可改善空间时，才运行 Candidate；
5. 首轮对照有正向信号后，才执行第二次重复。

任一阶段出现协议、安全、数据泄漏或系统性失败时立即停止，不继续消耗模型调用。
统一实时评测入口默认 `--max-samples 2`；执行 8 案例或 16 样本前必须显式提高该上限，避免误操作直接启动批量计费。
