# PG 真实模型效果评测：有局部正向信号，尚未证明稳定收益

## 结论

2026-10-31 完成 24 次 test 执行、4 次 dev 执行和 1 次 Refiner 调用，共 146 次模型尝试。关闭 PG 正确完成 1/8，V4 种子图正确完成 2/8，学习后保留图正确完成 2/8。但本轮没有保留新图，第三组与第二组实际使用完全相同的图，不能作为自进化收益证据。

三组都没有任何一道题两次重复均成功。种子组相对基线多成功一次，模型调用增加 16.7%，Token 增加 34.9%，未通过预先冻结的成本非回退门槛。样本很小，也存在明显的前置理解失败，不能据此宣布 PG 稳定提高准确率，更不能保证复杂任务成功。

最值得优先修复的是语义输出协议与执行条件的衔接：19 次 test 失败全部发生在商品检索前。PG 后续行动选择尚未得到充分检验。本轮只能说明当前集成的端到端表现，不能推断 PG 论文机制本身无效。

## 被测版本与范围

- Runtime 源码提交：`6c0f611fd1053e5d04a99b20a43eb96454c1221a`，在 `codex/complex-task-semantics-v1` 既有成果上进行后续验证；生产 Runtime 未改动。
- 三组统一使用当前 Gateway 配置，实际调用为 `openai_compatible / deepseek-flash`。每 Run 上限为 16 次模型调用、90 秒、256000 输入 Token 和 12000 输出 Token，单次 Provider 尝试一次。
- baseline 为 `adaptive-v1`，PG 为 `adaptive-pg-context-v4`，种子为 `pg-seed-v2.json`；不混入 V6 预演，不测 ACE 或 LivePlan。
- 数据为 4 道新编写的 test 题，每题每组重复 2 次。它们是虚构商品目录中的新约束组合，覆盖单轮选购；未覆盖真实开放目录、支付退款和多轮长程任务。
- 训练 2 题、验证 2 题，均为 dev；Refiner 只读训练题。test 开始前冻结图和对照契约，执行期间没有修改源码、Prompt、模型或预算。
- 每个样本使用独立 SQLite。人工约束、实际商品数据、目标账本、独立审核和轨迹协议共同判分，不采用 Agent 自报成功作为唯一依据。

## 失败发生在哪里

24 个 test 样本中，5 个完整通过，19 个失败：

| 终止类别 | 数量 | 原始证据 |
| --- | ---: | --- |
| 独立需求提取协议失败 | 15 | `request_semantics_rejected`；终止为 `WAITING_CLARIFICATION` |
| 需求条件被标为未知 | 2 | T01 的 PD 功率条件被提取为 `UNKNOWN` |
| 规划修复预算耗尽 | 2 | `DECISION_REPAIR_BUDGET_EXHAUSTED` |

这 19 次均未进入 `search_products`、`discover_products` 或 `compare_products`；仍可能已经读取 `get_catalog_facets`，因此不能说完全没有工具调用。

主要校验错误包括：目录概念只能完整未绑定或完整编码、执行字段和值与可信概念编码不一致、字段不符合协议、条件缺少明确目标。当前协议允许同时携带语义概念与执行字段，二者的一致性要求未稳定满足；这是接口可靠性问题，不能仅归咎于用户问得复杂。

商品夹具中已有 `PD 供电`，通用谓词能表达这个约束，但冻结概念注册表没有对应功率概念，提取器两次选择了 `UNKNOWN`。T01 因而同时测到了能力描述覆盖不足，不能把它的失败纯粹归因于 PG。仍保留在预先冻结的分母中，没有事后删题或据此调参。

## 恢复能力不能按表面指标解读

原始 `behavior_metrics` 中，基线扰动触发 0 次，两个 PG 组各触发 2 次并全部通过；它的 `recovery_rate` 分母仅含实际触发样本。基线大多在检索前失败，不能把“PG 100% 恢复”与基线直接比较。按全部扰动题计算，基线完成 0/4，两个 PG 组各完成 2/4。

T03 确实发生了一次空结果，两个 PG 成功样本随后重新检索并完成任务。但关键重试的 `pg_decision_reviewed.status` 为 `UNKNOWN`，`matched_edge_ids` 为空；这支持“整个 Agent 能恢复”，不支持“这次恢复由 PG 推荐边导致”。

T04 的两次成功运行均将 `P1309S` 和 `P1301S` 的库存清零；它们不是最终推荐的 `P1303`，接口数也不满足本题条件。因此本轮验证了扰动环境下的最终结果正确，没有充分检验“既有有效候选失效后重新规划”。下一版应预先冻结针对合格候选的失效注入，不能事后把这两次成功当成强恢复证据。

## 自进化结果

开发集 4 次执行正确完成 1 次，种子验证为 0/2。Refiner 依据训练轨迹提出修改 `inspect-recommend` 的适用条件，但 `hypothesis.target_edges` 同时列出了 `search-inspect`，实际补丁仅修改 `inspect-recommend`。提案以 `HYPOTHESIS_TARGET_MISMATCH` 被拒绝，未进入候选验证，也没有接受任何新图。

种子与保留图 SHA-256 均为 `67cd653380aad6c16e90d2f1a8ccbd1792d7658d5d683642fa111ae86112b869`。不能用第三组 2/8 的结果称为“学习后提高”；它只是相同图的独立重复。

## 评测驱动修正与证据完整性

首次启动 `run-01` 将图放在不支持的目录，在任何模型调用前被拒绝。修正存储位置后开启全新的 `run-02`；首次启动产物未删除。

`run-02` 的原汇总还发现一个纯报告问题：冻结驱动用了 PG 的紧凑 JSON 哈希，live evaluator 使用带空格的 JSON 哈希，因此原 `summary.json` 把全部组误报为数据身份不符。对同一个未修改的数据文件重新计算，两种算法分别与原冻结文件及全部原始报告一致。

真实调用全部结束后，仅修复驱动今后的哈希选择，添加回归断言，并生成 `reporting-correction.json`、`test-frozen-corrected.json` 和 `summary-corrected.json`。没有修改原始报告、题目、判分、阈值或任何模型结果，也没有额外调用模型。

更正后的跨组可比性检查没有错误；种子组仍因调用增加 6 次而未过成本门槛，演化组因未产生新图而无演化结论。总体 `INCONCLUSIVE`、`candidate`，没有晋升。`evidence_valid=false` 是当前汇总将门禁未过合并到该字段的结果，不表示原始运行伪造；具体失败原因须看 `comparison.gates`。

## 下一阶段优先项

1. 收紧模型输出接口，让模型表达语义概念、运算和数值，由确定性代码编译执行字段；保留独立需求核验，减少模型重复生成两套必须完全一致的字段。内部协议失败应有可恢复错误分类，不能统一要求用户澄清已经清楚的需求。
2. 补齐目录能力描述与单位编码的一致性，解决“数据有字段、语义能力目录没有字段”的落差，避免逐句增加规则。
3. 修复 Refiner 假设和补丁的结构一致性反馈，确保有界修复发生在独立 dev 验证之前。不能手工修改这次提案后称为模型自进化成功。
4. 修复后冻结新留出集，并增强有效候选失效注入，再做多次、更多题目的 PG 对照。本次 test 已用于诊断，后续只能作为已见回归集，不能继续称为未见测试。
